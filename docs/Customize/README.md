# カスタマイズ実装をコードから理解する

調査日: 2026-11-13。対象は本プロジェクトのその時点の作業ツリー。これは設計提案ではなく、実装を読むための資料である。

## 到達点と資料の範囲

目的はクラス名を覚えることではない。「入力がどの変数を変え、その値がどの経路で画面・ファイルに届くか」を自分で追えるようになること。

読む順序:

1. [オブジェクトと実行の仕組み](01-Objects-And-Execution.md)
2. [操作をコードで追う](02-Operation-Walkthrough.md)
3. [技術と調査の手引き](03-Technology-And-Reading.md)

現版は、カスタマイズの全体構造と主要操作を深く読むための解説である。**全ファイル・全関数の網羅的な仕様書ではない。** 特にIKソルバー内部の全分岐、JSONパーサーの全関数、描画APIの全引数を検証し終えた資料ではない。未解説の関数まで理解済みと判断する根拠にはしない。

コードの挙動を変更する作業は行っていない。設計意図として説明する理由は、現在の責務とデータの流れから読み取れる理由であり、すべての過去の実装経緯を保証するものではない。

## 最初に理解する5つの区別

|混同しやすいもの|この実装での違い|
|---|---|
|Sceneと画面|CustomizeSceneは一つ。メニュー・カテゴリ・技編集などはFlowのmodeで切り替える内部画面|
|Controllerとゲームパッド|ControllerはC++の制御担当オブジェクト。入力機器そのものではない|
|ControllerとSystem|Controllerは編集状態や画面の進行を保持する。対戦Systemの全オブジェクト一括更新と同じ方式にする必要はない|
|下書きと保存データ|画面操作はメモリ上のdraftを編集する。保存APIを呼ぶまではJSONへの書込みではない。ただしID移行処理には別途書込みがある|
|描画姿勢と保存姿勢|前者は補間・スキニングの計算結果。後者はモーションのキーフレーム。毎フレームの表示行列を全部保存しているわけではない|

## ソースを開く順序

ソースルートは `DrectX11Sample/Source`。

| 最初に開くファイル                                      | 読む目的                          |
| ---------------------------------------------- | ----------------------------- |
| Scene/CustomizeScene.cpp                       | Sceneが実処理を委譲していることを確認         |
| Controller/CustomizeFlowController.h           | 誰を所有し、どの状態を保持するか確認            |
| Controller/CustomizeFlowController.cpp         | RunSystems・Drawから各操作の呼出順を追う   |
| UI/CustomizeAttackEditorView.cpp               | 専用UIがどの値を編集し、何の操作結果を返すか確認     |
| UI/CustomizeMotionEditorControls.cpp           | キー追加・プリセット等のボタンと編集APIの接続を確認   |
| Controller/CustomizeMotionEditorController.cpp | 姿勢キー・移動キー・IK結果が下書きへ反映される箇所を確認 |
| Controller/CustomizePreviewController.cpp      | 表示用の姿勢・カメラ・ギズモの計算を確認          |

コードの行番号は更新でずれるため、本文ではファイルと関数名を検索キーにする。
