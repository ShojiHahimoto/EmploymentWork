# 3. 技術と調査の手引き

## 技術名をコードと結び付ける

### イミディエイトモードUI

ImGuiはそのフレームに部品を登録し、Button等の結果をその場で使えるUI方式。手軽だが、Draw関数に保存やmode変更が混ざりやすい。現在のキャラクター編集・一部のスロット一覧にはこの経路が残る。

専用UIも部品のフレーム登録を使うが、Rootが状態を持ち、更新で操作を解決して描画命令へ渡す。見た目を変更しただけで、すべての画面の入力依存がImGuiから消えたわけではない。Previewのカメラ入力、マーカー、ImGuizmoは別に読む。

### 入力捕捉とフォーカス

フォーカスはキーボード・パッドの操作対象。ポインター捕捉は「押し始めたボタン」を解放まで追う状態。押したボタンから外れて離したとき、別のボタンを誤発火させないために区別する。

UIInputSystemはWin32の文字・マウスイベントとUIアクションをInputFrameへまとめる。RootはBeginFrameでそれを受け、部品登録後にEndFrameで確定する。WasActivatedは確定した操作を問い合わせる。

### ローカル座標とワールド座標

ローカルは親を基準とする値、ワールドは共通空間上の値。手のローカル回転を変えると、その子やメッシュの計算結果が変わる。IKの目標がワールドだからといって、保存する回転もワールド回転とは限らない。

ボーンのモデル内行列と、キャラクター全体のTransformも別。モデル内の関節位置を画面へ投影するには、キャラクターのワールド行列、カメラのView/Projectionまで通す。

### FK・IK

FKは親から子へ姿勢を伝える計算。肩を回すと肘や手が追従する。IKは「手をここへ置きたい」という目標から親関節の回転を求める計算。IKを使って作った姿勢も、表示には階層を通した姿勢計算が必要になる。

IKは任意の目標へ必ず到達できる魔法ではない。骨長と可動域と固定条件があるため、届かないときの誤差や停止条件も正常な結果の一部になる。

### Quaternion

軸角や回転の合成に使う4成分の回転表現。表示用Euler角の3値と同じ意味ではない。Eulerへ変換した数値が飛んでも、姿勢が飛んだとは限らない。一方、保存前にEulerへ戻して制限すると姿勢自体へ影響する可能性があるため、このプロジェクトでは姿勢のQuaternionを正として扱う。

Quaternionの各成分を単純な角度として足し引きしてはいけない。回転合成の順序や軸の座標系は、実際の乗算と変換関数を読む必要がある。

### 補間とサンプリング

キーのないフレームで前後のキーから姿勢・位置を求める処理が補間。特定時刻の値を取得することをサンプリングと呼ぶ。「Sample」はテスト用の仮処理という意味ではない。

位置は線形補間、回転は回転用の補間を区別する。先頭キーより前、最後のキーより後、ループの終端は通常のキー間とは別条件になる。MotionPoseやモーションデータの評価処理で確認する。

### スキニング

スケルトンの行列から頂点を変形する処理。編集部位15個だけでメッシュ全頂点を直接動かすわけではない。編集部位名を実FBXのボーンへ対応付け、骨階層の姿勢から描画用行列を作り、モデル描画へ渡す。

ModelResourceは共有のモデル情報。SkeletonPoseは表示対象ごとの姿勢。共有モデルそのものを書き換えると別オブジェクトへ影響するため、この区別が重要になる。

### 9スライスと描画キャッシュ

9スライスは画像を四隅・辺・中央へ分け、角を不用意に伸ばさずパネルの寸法を変える方法。単なる画像全体の拡大とは違う。

UIRendererのキャッシュは描画要求の再ラスタライズ等を省くためのもの。編集draft、MotionDataの共有キャッシュ、スキニング行列、Undoのスナップショットはそれぞれ目的が違う。「キャッシュ」と呼ばれていても消してよいタイミングは共通ではない。

## 調査例: 「プリセット適用が保存まで見えない」

1. ボタンを押したか: Viewの操作分岐を確認。
2. 適用対象キーが存在するか: HasMotionKeyframeと内部/表示フレームの変換を確認。
3. draftに値が入ったか: MotionEditorの適用処理を確認。
4. 配列が評価側の前提を満たすか: キーの時刻順を確認。
5. Previewへ同じdraftが渡るか: Flow::RenderAttackPreviewの引数を確認。
6. 表示姿勢の再計算が行われたか: PreviewからMotionPoseへの経路を確認。

保存すると直るからといって、ファイル読込が原因とは限らない。保存時の正規化が、メモリ上の不整合を偶然直している可能性がある。

## リファクタリング前に固定すべき観察点

- ある操作がUpdateで確定するか、Drawで確定するか。
- 戻り値はデータ、要求、成否、メッセージのどれか。
- 参照引数と所有メンバーのどちらを変えるか。
- キーの内部フレームと表示フレームをどこで変換するか。
- 入力中の一時状態を、画面切替・Undo・部位変更時に誰が終了するか。
- ファイル保存とキャッシュ破棄が別の経路からも起こるか。

## 現状の注意点と改善候補を区別する

現状: Draw側にギズモ結果の取込みがある。改善候補: 入力更新へ移す。ただしImGuizmoのフレーム進行と即時表示を理解する前に移動しない。

現状: 保存結果の文字列接頭辞で成功判定する。改善候補: 成否と表示メッセージを別の型にする。メッセージ文面だけを変更すると呼出側が失敗と判断するため、同時に変更する必要がある。

現状: Flowが複数責務の接続を持つ。改善候補: 編集セッションの管理を分ける。ただし単純に関数を別ファイルへ移しただけで責務が分離されたとは言えない。

これらは本資料でコード変更を行う提案ではない。現状を読み終えてから比較するための観点である。

## 自力で理解したと判断するための課題

1. 回転ギズモの出力からJSON保存まで、実際の関数名を挙げて説明する。
2. 攻撃の位置キーと手首IKが同じ保存データではない理由を説明する。
3. 技名のUI編集値・draft・JSONの3か所を特定する。
4. フレームを切り替えたとき、古いドラッグ状態を残すと何が起こるか説明する。
5. 保存結果メッセージを変更する場合、どの呼出側を調査するか挙げる。

答えを言葉だけでなくコードの代入箇所と呼出箇所で示せれば、単なる設計メモの理解から一段進んでいる。
